# ADR-003. Kiwi 형태소 BM25 + RRF + Cross-Encoder 리랭킹

- 상태: **채택**
- 날짜: 2026-10-03
- 관련: ADR-002(인제스천 그래프), `src/finrag/index/bm25_ko.py`, `src/finrag/retrieval/hybrid.py`, `src/finrag/retrieval/rerank.py`

---

## 맥락

**무엇이 문제였나.** 3회차 Dense(BGE-M3) 단독 검색은 골든셋 40문항에서 Recall@5 77.5%,
MRR 0.555 였다. 정답이 후보 5개 안에는 들어오지만 1등은 40% 만 맞춘다. 금융 약관 질문의
핵심 단서는 조항번호·상품명·회사명·숫자인데, 임베딩은 이것을 "비슷한 뜻"으로 뭉개 버려
같은 발행사의 다른 조항, 다른 판본, 다른 상품이 위로 올라온다. 5회차부터 에이전트가 상위
몇 개만 읽고 답하므로 **1등이 정답이어야** 한다.

baseline 이 놓친 문항 가운데 셋을 뜯어 보면 Dense 가 무엇을 못 보는지 드러난다.

| 문항 | 질문의 단서 | Dense 가 놓친 이유 | baseline MRR → Hybrid MRR |
|---|---|---|---|
| S02 조항번호형 | "**ABL** 인터넷암보험Ⅲ 약관 **제34조** 해약환급금" | 1등이 다른 보험사 실손 표준약관의 제34조(`sonsa_silson_std_2024`)였다. "제34조 해약환급금"이라는 뜻만 보고 회사명을 무시했다. BM25 는 ABL·암보험 토큰으로 문서를 맞췄고 리랭커가 1등으로 올렸다 | 0.25 → 1.00 |
| S33 계산형 | "iM뱅크 **가계대출** 1억 2천만원, 약정 5%, 가산 3%, 2개월 **연체**" | 1등이 같은 은행의 다른 상품 설명서(`im_mortgage_2024` 주택담보대출)였다. 숫자가 많은 질문은 벡터가 평균으로 뭉개져 "iM뱅크 대출 이자" 정도만 남는다. Kiwi 가 "연체이자율"을 사전 낱말로 통째로 잡아 가계대출 설명서의 연체 조항을 올렸다 | 0.00 → 1.00 |
| S30 복합형 | "하나은행 주택담보대출 2년 11개월 시점 **중도상환해약금**" | 문서는 맞췄지만 청크가 틀렸다(상품 개요 청크가 1등, 정답은 3위). Kiwi 기본 분석은 중도/상환/해약/금 으로 쪼개지만 사용자 사전으로 통째로 잡아 BM25 가 정확히 그 조항을 올렸고, 리랭커가 1등으로 확정했다 | 0.33 → 1.00 |

측정된 사실:

| 무엇 | 값 | 출처 |
|---|---|---|
| Dense 단독 Recall@1 / Recall@5 / MRR | 40.0% / 77.5% / 0.555 | `results/baseline.json` |
| 공백 분리 BM25 Recall@5 / MRR, 어휘 | 42.5% / 0.289, 50,963개 | `make bm25-compare` |
| Kiwi 형태소 BM25 Recall@5 / MRR, 어휘 | 57.5% / 0.444, 9,794개 | `make bm25-compare` |
| Dense + Kiwi BM25 (RRF 만) Recall@1 / MRR | 35.0% / 0.526 | `results/hybrid_norerank.json` |
| + 리랭커(bge-reranker-v2-m3, 후보 10) Recall@1 / MRR | 62.5% / 0.693 | `results/hybrid.json` |

> 눈여겨볼 것: **RRF 만 붙이면 MRR 이 baseline 보다 떨어진다**(0.555 → 0.526). BM25 가
> 후보를 넓혀 주지만 순서까지 좋게 만들지는 못한다. 순서는 리랭커가 바로잡는다.

## 대안

| # | 대안 | 장점 | 단점 | 왜 안 골랐나 |
|---|---|---|---|---|
| A | Dense 단독 유지(baseline) | 지연 281ms, 구성 단순 | Recall@1 40%. 조항번호·숫자 질문을 구조적으로 못 본다 | S02·S33·S30 류를 고칠 수단이 없다 |
| B | 공백 분리 BM25 + Dense | Kiwi 없이 인덱스 0.1초 | "제15조의"와 "제15조"가 다른 토큰. BM25 단독 Recall@5 42.5%, Kiwi 는 57.5% | 조항번호형이 핵심인 코퍼스에서 15%p 를 버릴 이유가 없다 |
| C | 점수를 정규화해 가중합(RRF 대신) | 점수 차이를 살릴 수 있다 | 코사인은 0~1, BM25 는 상한 없음. 질의 길이·문서 수에 따라 가중치가 흔들려 질의마다 다시 맞춰야 한다 | 재현되지 않는 튜닝 축이 하나 늘어난다. RRF 는 순위만 써서 매개변수가 k 하나다 |
| D | Kiwi BM25 + RRF, 리랭커 없음 | 지연 690ms, 모델 2.2GB 불필요 | Recall@1 35%, MRR 0.526 으로 **baseline 보다 낮다** | 후보는 넓어지는데 1등 품질이 떨어진다. 에이전트가 읽는 건 1등이다 |
| E | Kiwi BM25 + RRF + Cross-Encoder 리랭킹(후보 10) | Recall@1 62.5%, MRR 0.693 | 지연 1311ms(baseline 의 4.7배), 메모리 +2.2GB | **← 골랐다** |

## 결정

> Kiwi 형태소 BM25 와 Dense 를 RRF(k=60) 로 합쳐 후보 10개를 만들고, bge-reranker-v2-m3
> 로 다시 정렬한다. 필터가 있으면 BM25 후보는 Dense 가 통과시킨 문서(doc_id) 안으로 제한한다.

후보 수 10 은 `make rerank-sweep` 결과다. 10 과 20 은 R@1 80%, R@5 90% 로 같고 MRR 은 10 이
0.017 높은데(0.867 vs 0.850), 리랭커 시간은 20 이 1.75배(941ms → 1648ms)다. 품질 득이 없는
비용은 내지 않는다. 기본값은 `.env` 의 `RERANK_CANDIDATES=10` 이다.

## 근거 지표

| 지표 | 전(baseline) | 후(hybrid) | 차이 |
|---|---|---|---|
| Recall@1 | 40.0% | 62.5% | +22.5%p |
| Recall@5 | 77.5% | 77.5% | 0 (후보 폭은 그대로, 순서가 바뀜) |
| MRR 전체 | 0.555 | 0.693 | +0.138 |
| MRR 조항번호형 | 0.750 | 0.833 | +0.083 |
| MRR 계산형 | 0.300 | 0.800 | +0.500 |
| 문항당 지연 | 281ms | 1311ms | ×4.7 |

측정 방법: 골든셋 40문항(`data/golden/`), `finrag.eval.harness` 로 Recall@k·MRR. 리랭커 지연은
문항별 `latency_ms` 평균.
재현 명령: `make index && make baseline && make bm25-compare && make hybrid-norerank && make hybrid && make rerank-sweep`

## 대가

| 잃은 것 | 얼마나 | 받아들일 만한 이유 |
|---|---|---|
| 지연 | 281ms → 1311ms (리랭커가 약 940ms) | 5회차 에이전트는 LLM 호출이 수 초라 검색 1초는 병목이 아니다 |
| 메모리 | 리랭커 2.2GB 추가 상주 | 8GB 노트북은 `RERANKER_MODEL=BAAI/bge-reranker-base`(1.1GB)로 바꿀 수 있다 |
| 첫 실행 비용 | Kiwi 토큰화 15초, 캐시 파일 생성 | 청크·토크나이저 해시로 캐시해 두 번째부터는 0초 |
| 필터 제약 | BM25 후보를 Dense 통과 문서로 제한하므로 Dense 후보 50개에 전혀 안 뜬 문서는 BM25 로도 못 찾는다 | 필터는 발행사·종류처럼 문서 수십 건 단위라 Dense 50개 안에 그 문서가 들어오지 않는 경우는 드물다 |

## 되돌릴 조건

- [ ] `results/hybrid.json` 의 전체 MRR 이 baseline(0.555) 아래로 내려가면 → 리랭커 모델 또는 후보 수를 다시 본다
- [ ] 문항당 지연이 3,000ms 를 넘으면(에이전트 한 턴에 검색을 여러 번 하면 체감된다) → 후보 수를 줄이거나 작은 리랭커로 바꾼다
- [ ] GPU 가 확보되면 → 후보 20 이상을 다시 재서 R@5 가 오르는지 본다. CPU 에서는 후보당 80~95ms 라 늘릴 수 없었다
- [ ] 문서 수가 500건을 넘으면 → rank_bm25 는 인메모리라 메모리와 토큰화 시간을 다시 잰다. Qdrant 서버의 sparse vector 로 옮길지 결정
- [ ] 5회차 Self-Query 로 LLM 이 필터를 뽑게 되면 → "BM25 를 Dense 통과 문서로 제한" 방식 대신 BM25 쪽에도 메타데이터 필터를 직접 거는 것이 맞는지 다시 본다

되돌리는 비용: `.env` 두 줄(`RERANK_CANDIDATES`, `RERANKER_MODEL`). 리랭커를 완전히 빼는 것은
`pipelines/hybrid.py --no-rerank` 플래그 하나. BM25 인덱스는 캐시라 재생성 15초.

## 결과

- 40문항 Recall@1 62.5%, MRR 0.693. 강사 참고값(MRR 0.652, Recall@1 55.0%)보다 조금 높게 나왔다.
- 실패 사례 3건(S02·S33·S30)은 모두 MRR 1.00 으로 고쳐졌다.
- 아직 0 인 문항: S13·S17(카카오뱅크 정기예금 **특약**의 가입대상·계약기간), S15(2013년판 하나은행 약관), S35(실손 표준약관 공제금액).
  S13·S17·S15 는 검색 품질이 아니라 **판본·문서 종류를 가려 주지 않아** 생기는 실패다. `search_demo --issuer 카카오뱅크` 로
  돌리면 2019 특판·2024 특약·2026 설명서가 섞여 나오고 `--latest` 가 2019 를 뺀다. 이것이 5회차 Self-Query(LLM 필터 추출)의 몫이다.
- RRF 만으로는 baseline 보다 떨어진다는 사실을 실측으로 확인했다. "하이브리드를 붙였으니 좋아졌겠지"라고 말하기 전에 `make hybrid-norerank` 를 돌려 볼 것.
